# Managed setup

The included Compose file runs local PostgreSQL 18 with pgvector, NATS JetStream, and ClickHouse. Its development ports bind to loopback. Start the infrastructure, apply schemas, and build the four executables:

```sh
docker compose up -d --wait
atlas migrate apply --dir file://atlas/migrations/postgres --url 'postgres://postgres@127.0.0.1:25432/nameserver?sslmode=disable'
python3 tools/migrate_clickhouse.py apply --url http://127.0.0.1:28123
cargo build --workspace --locked
```

PostgreSQL migrations create separate `nameserver_admin` and application roles. For an external installation, configure credentials and authentication through your database administrator. The sample infrastructure is for local development. Keep the unauthenticated management API and NATS private, or put them behind authenticated access.

The examples reserve 256 MiB for the JetStream flow stream through `nats.flow_max_bytes` (under `management.nats` on DNS nodes). Without that setting, the default is 10 GiB; the broker must have enough available storage to reserve it. Use the same value across nodes. Provisioning preserves an existing stream's limits, so change an existing stream through NATS administration when adjusting its capacity.

Start these in separate terminals:

```sh
target/debug/nameserver-control --config examples/control.toml
target/debug/nameserver-authority --config examples/authority-managed.toml
target/debug/nameserver-resolver --config examples/resolver-managed.toml
```

The CLI defaults to the management API at `http://localhost:8080`. Use `--url` or `NAMESERVER_CONTROL_URL` to select another endpoint.

```sh
target/debug/nameserver zone dnssec keygen
target/debug/nameserver zone apply examples/managed-zone.toml --yes
target/debug/nameserver zone list
target/debug/nameserver zone dnssec ds example.test
target/debug/nameserver profile create Personal
target/debug/nameserver profile list
```

Profile IDs are generated by the control plane. Use an ID from `profile list` with `profile block`, `profile allow`, and `profile apply --yes`. Each command's `--help` documents its arguments. Set `management.default_profile` to that ID to apply it to ordinary DNS requests. Without a selected profile, management traffic uses unfiltered recursion; local `[filters]` files still apply.

For per-device encrypted DNS, configure TLS as described in [configuration](configuration.md), set `server.tls.dns_name` to the base hostname, and use `https://base-host/profile-id` for DoH or `profile-id.base-host` for DoT. The certificate must cover the hostname in use. Unknown profiles do not fall back to unfiltered resolution.

## Updates and outages

`profile apply`, filter compilation, and zone apply publish through NATS. Resolver filters and profiles reload without restarting the DNS process. Invalid compiled custom lists make the profile unavailable instead of silently disabling its policy. Managed zones are rebuilt and signed before an atomic catalog swap; failed updates retain the last working catalog. Deleting a managed zone key removes that zone from service. Missing KSK or ZSK material rejects an enabled-DNSSEC update.

Local file changes use `SIGHUP`. Listener and access settings require a restart. Initial managed startup requires NATS; standalone mode does not. Run `--check` with local configurations to validate without listeners. Managed startup also verifies broker data; ACME mode can issue or renew a certificate when starting or checking its configuration.

## Database migrations

PostgreSQL uses the tracked Atlas directory. ClickHouse uses `tools/migrate_clickhouse.py` because the distributed Atlas ClickHouse driver requires account access. Both retain versioned SQL under `atlas/migrations/`.

The ClickHouse runner verifies hashes of all previously applied files before applying new statements and records each completed statement. A changed or missing applied file is rejected; add a new migration for schema changes. Run one migrator at a time per database. ClickHouse DDL and the history insert are separate operations: if a connection fails after the DDL commits, inspect the database and history before retrying. `status` reports pending statements without changing the schema. `NAMESERVER_CLICKHOUSE_USER` and `NAMESERVER_CLICKHOUSE_PASSWORD` supply HTTP credentials.

## Optional workers and models

`auto_pull`, `auto_rdap`, `injector.enabled`, `benign_sampler.enabled`, and `ml.enabled` default to false. Enable automatic feed polling after configuring your sources. Manual source pull, compilation, RDAP, and inspection commands remain available.

Build the inference feature and assemble the tracked runtime artifacts:

```sh
cargo build -p nameserver-control --features ml --locked
python3 tools/bundle_models.py
```

Install ONNX Runtime 1.24 or newer with API 24 support and set `ORT_DYLIB_PATH` to its shared library. The Rust feature loads it dynamically. Set `[ml] enabled = true` in the control config; the example model path points to the generated bundle. Model paths are relative to the config file. Enabling ML in a binary built without that feature is a configuration error.

The model bundle includes the tabular classifier, classification CNN, contrastive CNN, and their metadata. Research and training dependencies are isolated in `ml/pyproject.toml`; use `uv sync --project ml --python 3.13` when running that tooling. The DNS services do not require Python, ML models, or ONNX Runtime.

For automatic certificate management, add `[management.tls]` to the resolver configuration with `mode = "acme"`, `acme_domain`, `acme_email`, and a writable `cert_dir`. Set `acme_directory = "staging"` for issuance testing. Use the existing Cloudflare DNS-01 settings for wildcard issuance; authoritative DNS-01 synchronization uses the NATS subjects shared with the authority. `[server.tls]` still supplies the base `dns_name`. The source can also use `mode = "manual"` with `cert_path`/`key_path`, or `self_signed` for loopback development.
